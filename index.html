On this page

Overview

The platform helps instructors and integrity officers answer two questions about a student text: does it reuse text from known sources, and is its writing style consistent with the claimed author. It was built in the research project Advancing Plagiarism Detection through Contextual Embeddings at SDU NLP, SDU University. See About the project.

It has three parts:

  • This web page. A similarity check and a style comparison that run in the browser with baseline methods. Use it for quick checks and for teaching what the scores mean.
  • The API server. A small HTTP service that scores texts with a contextual embedding model. This is the part that detects paraphrased passages. Other systems call it.
  • LMS integration. A documented way to call the API from Moodle, Canvas or any other platform when a student submits work.

Quick start for instructors

  1. Open Similarity check. Paste the student text into Submission.
  2. Paste each reference text into a Source box and give it a short name. Use Add a source for more.
  3. Select Run check. Read the matched-text share first, then the per-source table, then the highlighted passages. Each highlight carries the number of its source.
  4. Use Copy, Download .txt or Print or save PDF to keep the report for a case file.
  5. To detect paraphrase, open Connect to the project API, enter your institution's API address and key, and select Test connection. Later checks add a sentence-level comparison by meaning.
  6. For a style question, open Authorship, paste the questioned text, add earlier work by the student and by at least one other writer, and select Compare style.

You can load .txt, .docx and text-based .pdf files. Scanned PDFs have no text layer and need OCR first. Texts may be in any language written with spaces between words, including Kazakh, Russian and English. The function-word feature in the style comparison covers English, Russian and Kazakh and is skipped for other languages.

How to read the scores

ScoreWhat it measuresWhere
Matched textShare of the submission's words that sit inside a word sequence (three words by default) also found in a source. Catches copied and lightly edited text.Page, API (containment)
JaccardShared three-word sequences divided by all three-word sequences in both texts. Low when the texts differ a lot in length.Page, API
Term cosineCosine between the word-count vectors of the two texts. High for texts on the same topic, even with no copying.Page
Longest runLongest unbroken stretch of matched words.Page
Flagged shareShare of submission sentences whose embedding has a cosine at or above the threshold with some source sentence. Catches paraphrase.API
Style similarityCombined closeness of two texts in character trigrams, function words and sentence and punctuation habits.Page

The page labels matched text below 15% as low, 15% to 40% as moderate and above 40% as high. These bands are a reading aid. Correctly quoted and cited passages also count as matches, so a reviewer always has to look at the highlighted text before drawing a conclusion.

Method

Lexical baselines

Texts are lower-cased and split into words. Every run of three consecutive words is a shingle. The page lets you raise this to four or five words to ignore short chance matches. Jaccard and matched-text share are computed from the two shingle sets. Term cosine uses raw word counts.

Contextual embeddings

The API splits each text into sentences and encodes every sentence with a transformer sentence encoder. Vectors are normalised, so the dot product of two vectors is their cosine similarity:

cos(a, b) = (a · b) / (‖a‖ ‖b‖)

For each submission sentence the API finds the most similar source sentence. A pair at or above the threshold (default 0.80) is returned as a match. Because the encoder represents meaning in context, a reworded sentence still lands close to its original, where the shingle methods see nothing. The second example source on the check page shows this gap: it is a paraphrase and gets a low lexical score.

Style comparison

On this page, style similarity is a weighted mean of character-trigram cosine (0.5), function-word cosine (0.3) and closeness of seven scalar habits such as mean sentence length and commas per 100 words (0.2). On the API, each author is represented by the mean embedding of their sentences and candidates are ranked by cosine to the questioned text.

POST/v1/compare

Compares one submission with 1 to 50 sources. threshold is optional.

curl -X POST http://localhost:8000/v1/compare \
  -H "Content-Type: application/json" \
  -H "X-API-Key: YOUR_KEY" \
  -d '{
    "submission": "Text of the student work ...",
    "sources": [
      {"id": "library-0142", "text": "Text of a reference document ..."}
    ],
    "threshold": 0.8
  }'
{
  "model": "sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2",
  "threshold": 0.8,
  "submission_sentences": 12,
  "overall_flagged_share": 0.25,
  "sources": [
    {
      "source_id": "library-0142",
      "lexical":  {"jaccard": 0.0412, "containment": 0.1037},
      "semantic": {"mean_best_cosine": 0.6121, "flagged_share": 0.25},
      "matches": [
        {"submission_sentence": "...", "source_sentence": "...", "cosine": 0.9134}
      ]
    }
  ]
}

The numbers above show the response shape. They are not measured results.

POST/v1/authorship

Ranks candidate authors by style similarity to a questioned text.

{
  "questioned": "Text whose authorship is in question ...",
  "candidates": [
    {"id": "student-17", "samples": ["Earlier essay ...", "Another essay ..."]},
    {"id": "student-23", "samples": ["Earlier essay ..."]}
  ]
}
{
  "model": "...",
  "questioned_sentences": 9,
  "ranking": [
    {"candidate_id": "student-17", "sentences": 31, "style_cosine": 0.8420},
    {"candidate_id": "student-23", "sentences": 14, "style_cosine": 0.7015}
  ]
}

Errors

  • 401: the X-API-Key header is missing or wrong.
  • 422: the body is malformed, a text exceeds 200,000 characters, or a text has no sentence of three or more words.

Connecting a learning management system

The API is stateless, so any platform that can send an HTTP request when a student submits work can use it. The flow is the same everywhere:

  1. Trigger. The LMS signals that a submission was created or updated.
  2. Extract. A connector reads the submitted file and converts it to plain text.
  3. Select sources. The connector gathers the comparison texts: other submissions to the same assignment, the institution's archive, and any course readings.
  4. Score. The connector posts the submission and sources to /v1/compare.
  5. Report. The connector stores the response and shows the instructor the flagged share and the matched sentence pairs next to the submission.

Moodle

Moodle provides a plugin type for this purpose, plagiarism. A plagiarism plugin receives assignment submissions through Moodle's event system, can queue work as a scheduled task, and can add a link or score beside each submission in the grading view. Implement steps 2 to 5 inside the plugin's task and keep the API address and key in the plugin's admin settings.

Canvas, Blackboard and others

Platforms that support LTI 1.3 can launch an external tool from an assignment. Host a small web application that receives the launch, fetches the submission, calls the API and renders the report. Platforms without LTI can call the API from a nightly script that reads submissions through the platform's own REST API.

Deployment checklist

  • Run the server on institutional infrastructure and serve it over HTTPS behind a reverse proxy.
  • Set API_KEY and give each connecting system its own network rule.
  • A GPU is recommended for large batches. The default model also runs on a CPU for single documents.
  • Send long documents in parts of up to 200,000 characters.
  • To let this website call your server from the browser, start it with CORS_ORIGINS=https://shiralikadyrov.github.io. Browsers block calls from an https page to a plain http server, so the API must be served over HTTPS.

Privacy and responsible use

  • This web page processes text in the browser. It sends nothing to a server unless you connect it to an API, and then only to the address you enter. It remembers that address on your device and never stores your texts or API key.
  • The reference API server does not write request texts to disk. Institutions that add logging or an archive should tell students and follow their data protection rules.
  • Replace student names with pseudonymous identifiers in id fields.
  • A score is a prompt for review. Decisions about misconduct belong to people who have read the passages and heard the student.

Known limitations

  • The browser checks miss paraphrase and translation. Use the API for those.
  • Short texts give unstable scores. Treat anything under about 150 words with caution.
  • Languages written without spaces between words are not tokenised correctly on this page.
  • Style comparison is affected by topic and genre. Compare texts of the same kind where possible.
  • The check only finds overlap with the sources supplied. It does not search the web.

Goal

To improve plagiarism detection by integrating contextual embeddings from transformer language models, so that a detector understands similarity of meaning and writing style and is not limited to matching identical strings.

Objectives

  • Objective 1. Develop contextual embedding models for a style-based AI detector.
  • Objective 2. Integrate contextual embeddings into plagiarism detection algorithms such as Jaccard and cosine similarity.
  • Objective 3. Validate and optimise the system with an academic corpus, and make it available to educational platforms with open documentation.

How the platform relates to the project

  • The similarity check exposes the baseline algorithms from Objective 2 in a form instructors can use without installing anything.
  • The API server described in the documentation is where the project's embedding models from Objective 1 are loaded and served to other systems.
  • The authorship view gives a first, transparent reading of writing style, the second research line of the project.
